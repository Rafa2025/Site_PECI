// Overview

What We Built

Modern datacenter infrastructure spans heterogeneous hardware, virtualised workloads, and networked devices. Understanding how a VM behaves under real load — and testing its limits in a controlled way — requires tooling that brings collection, stress, benchmarking, and analysis into a single, extensible platform.

This project delivers a modular, extensible platform for infrastructure observability and performance testing. On one side, a Telegraf-based collector pipeline ingests metrics from multiple sources simultaneously — each new source requires only a container image and a configuration file, with no changes to the storage or orchestration layer. On the other side, a performance testing system built on Argo Workflows and k3s runs containerised stress and benchmark modules against target VMs, delivering structured results via HTTP callback. Both systems are integrated in a unified React dashboard and designed to produce labelled, timestamped datasets as the foundation for future ML-driven analysis.
01

Dynamic Observability

Multi-source metrics collection via Telegraf pods orchestrated by Argo Workflows. Each source — Proxmox, Scaphandre, PDUs — runs as an independent pod. Adding a new source requires only a container image and a WorkflowTemplate. InfluxDB stores all metrics; Grafana correlates them with active test runs.

02

Stress Testing

Four containerised stress modules (CPU, Memory, IO, Network) scheduled on worker VMs via Argo. Resource validation runs before each test to prevent over-provisioning. Structured error callbacks report OOMKill, image pull failures, and bad parameters. k6 runs HTTP load against QuickPizza in parallel to measure application degradation.

03

Performance Benchmarking

Five containerised benchmarks (STREAM, 7-zip, iperf3, fio, LMbench) characterise each worker VM before stress tests run. Results arrive via HTTP callback with raw scores, anomaly flags, and a diagnosis field. Baselines are stored per node and per benchmark type, enabling comparison across nodes and over time.

04

Intelligent Analysis

The platform is designed for ML readiness from the start. Every run is labelled, timestamped, and stored. Stress run windows provide ground truth for supervised models. Future work includes saturation forecasting, anomaly detection, and bottleneck identification using the accumulated run history.

// Design Principles

Modularity & Extensibility

Both systems follow the same principle: adding a new source, module, or benchmark requires only a new container image and a definition file. The orchestration, storage, and UI layers remain unchanged.

Collector — Telegraf Plugin Model

Each data source is a Telegraf pod with its own input plugin configuration. Proxmox, Scaphandre, and PDU pods run simultaneously and independently. A new source — GPU, containers, SNMP switch — requires a new container image and a WorkflowTemplate. No pipeline changes.

Stress & Benchmark — WorkflowTemplate Pattern

Every test and benchmark is a containerised WorkflowTemplate. Adding a new stress profile or benchmark requires only a Dockerfile and a YAML definition. The UI, backend, and Argo configuration require no changes. SPEC CPU 2017 will follow the same pattern when the license is acquired.

Node Scalability

Adding a new worker node to the k3s cluster is three commands. Container images pull automatically from ghcr.io on first run. No pre-install, no host configuration, no NFS setup. Every benchmark and stress module is immediately available on the new node via the target-node parameter.

Data-Driven by Design

Every run is labelled with a workflow name, timestamp, node identifier, and test parameters. The Run Indexer attaches metadata to each execution. Stress windows provide ground truth labels for future ML models — the dataset forms automatically as the platform is used.

// Future Sources

Extensibility Roadmap

The Telegraf plugin model makes the following sources straightforward additions — each needing only a new pod configuration.

Containers & Microservices Per-container CPU, memory, and network via Docker or containerd input plugins — workload-level observability independent of the VM.
GPU Utilisation, memory, temperature, and power draw per card via the nvidia_smi plugin — relevant for ML inference workloads.
Network-Attached Devices Interface counters, error rates, and queue statistics from switches and routers via SNMP. Wireless APs via vendor APIs.
Latency Round-trip and DNS resolution latency via ping and dns_query plugins, complementing the bandwidth metrics already collected.
Storage & NFS NFS mount statistics and distributed storage health for shared storage pools. Disk health via SMART plugin.
IoT & Edge Sensor data from IoT devices via MQTT plugin. Industrial sensors and PLCs via Modbus — common in datacenter power and cooling.
